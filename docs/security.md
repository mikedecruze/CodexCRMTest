# Security

Local demo is for synthetic data only. Explicit TROVE_DEMO=1 exposes named fixture sign-in; NODE_ENV=production refuses demo mode. It is not Microsoft authentication. Normal mode disables all fixture sign-in endpoints and requires Entra configuration. An Entra user must match an active pre-provisioned Employee subject; token claims never grant application roles or admin by themselves.

Production OIDC uses openid-client discovery, PKCE S256, state, nonce, short-lived one-use login attempts and a confidential client secret supplied securely. Session tokens are random, stored hashed in SQLite, expire after eight hours, are cleared on logout, and use HttpOnly + SameSite=Strict; Secure is required outside demo. Mutations enforce an explicit same-origin allowlist, JSON request bodies, size limits and Zod schemas. No CORS wildcard, no raw token logging. Authorization uses current team memberships, explicit group grants or administrator exception. Associates read only; inactive/unassigned users cannot see client records. Admin manages lookup definitions and team membership.

All group detail, search, graph, record lookup, stats, write and audit requests authorize on the server. Unauthorized IDs return generic 404. Global lists project only visible group associations. Shared master records carry no confidential group fields. Relationships, notes and history are group scoped. Master edits require authority over every associated group; errors never name hidden associations. Visibility of a historical graph is still governed by today's access rights. Queries and graph payloads cannot expose other families sharing an entity/advisor.

Audit captures material changes atomically with business writes; no public delete endpoints exist. No SSNs/bank credentials are collected. Local SQLite is not a production multi-user Fabric store. The checked-in tests cover role writes, cross-family ID access, shared records, search/graph/audit leaks, interval rules, forged identity inputs and signed-out access. Real Entra/Fabric, tenant permissions, SharePoint and production transport must be validated separately before real client data.

OIDC protocol tests use a simulated HTTPS issuer and generated RSA signing keys. They exercise valid token exchange, PKCE forwarding, state/nonce checks, audience and tenant restrictions, expiry, forged signatures, replay and unprovisioned identities. These tests do not establish connectivity or consent in a real Microsoft tenant. Demo and Entra sessions carry separate server-side modes; a demo cookie cannot authorize requests after switching to Entra mode.

At validation, `npm audit --omit=dev` reported zero runtime vulnerabilities. The Microsoft CLI development dependency carries the upstream moderate sprintf-js precision-specifier DoS advisory through tedious; the registry offered no patched sprintf-js release. No verification was disabled or arbitrary SDK downgrade applied. This development-tool advisory is not a claim that deployment is production approved.

## Phase 2 financial access

Profitability checks require current Client Group authorization and either Partner/Director level, the current primary Relationship Manager assignment, or an explicit effective-dated profitability scope. Administrator status alone does not grant margin/labor-cost access. An explicit scope cannot grant the underlying Client Group authorization; an administrator must assign that separately. Revocation immediately blocks current and historical profitability views.

Restricted amounts are omitted from financial overview and trend payloads. Direct history and override routes reject unauthorized profitability requests; there is no client-only security filter. Audit records for restricted changes carry a PROFITABILITY classification and are filtered before returning them. Portfolio totals are omitted when any selected group is outside the user's profitability scope. Shared entities/advisors grant no access to another family's financials. Source mappings, imports, settings and permission grants require administrative authorization; ingestion additionally enforces classification per target group.
